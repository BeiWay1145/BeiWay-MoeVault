# 图库/主目录操作逻辑改版方案（资源管理器风格）

> 状态：**构想阶段，未实施**。待确认后实装。

## 一、可行性结论

**总体可行，改动幅度中等偏上（约 600–900 行，集中在 4 个文件）。**

| 需求 | 可行性 | 难度 | 说明 |
|------|--------|------|------|
| 去掉多选/全选按钮，改快捷键 | ✅ 完全可行 | 低 | 现有 `library.multiSelect` 状态可直接删除 |
| 单击图片下方信息区单选 | ✅ 完全可行 | 低 | 只需拆分点击区域（缩略图 vs 信息区） |
| Ctrl+左键叠加选择 | ✅ 完全可行 | 低 | 纯前端事件处理 |
| Ctrl+A 全选 | ✅ 完全可行 | 低 | 需处理输入框聚焦时不拦截 |
| Shift+左键范围选择 | ✅ 完全可行 | 中 | 需要"最后点击锚点"状态（现有代码无此概念） |
| 框选（拖拽橡皮筋） | ✅ 可行 | **中高** | 需自绘选择框 + 命中检测；瀑布流布局下坐标计算略复杂 |
| 拖出到资源管理器（复制） | ⚠️ **需验证** | **高** | Web 端 `DataTransfer` 无法携带真实文件路径；见下文风险 |

## 二、逐项实施方案

### 1. 去掉多选模式按钮，改快捷键

**现状**：`stores/library.ts` 有 `multiSelect` 状态；`LibraryView` 有复选框式的多选开关与"全选"复选
框；`onCardClick` 在 `multiSelect` 为 true 时走 `toggleSelect`，否则进详情页。

**改法**：
- 删除 `multiSelect` 状态与相关 UI（多选复选框、全选复选框）
- 新增 `lastAnchor: number | null`（Shift 范围的锚点）
- 新增统一的选择动作函数（见下）

**影响文件**：`stores/library.ts`、`LibraryView.vue`、`ImportDirectoryView.vue`

### 2. 点击"信息区"单选

**现状**：`ImageCard.vue` 整卡一个 `@click`。

**改法**：把卡片分为两个命中区
- **缩略图区**（`.thumb`）→ 打开详情（保持现有行为）
- **信息区**（`.meta`：名称/分辨率/大小/清晰度）→ 单选该图

`ImageCard` 新增 `@select` 事件，`.meta` 上绑定点击并 `@click.stop` 阻止冒泡到卡片。

**注意**：需求明确"点 A 再点 B 会取消 A"——即信息区点击是**替换式单选**（不叠加）。

### 3. Ctrl+左键（叠加选择）

- 在缩略图或信息区按住 Ctrl 点击 → 切换该图的选中状态（已有则取消，没有则加入）
- 重复点击同一张 → 反复切换（满足"重复该单选可以达到多选"）

### 4. Ctrl+A 全选

- 全局 `keydown` 监听；当焦点在 `input` / `textarea` / `contenteditable` 时**不拦截**
- 全选范围 = **当前显示的图片列表**（`library.images`），不含跨页未加载项

### 5. Shift+左键（范围选择）

- 记录 `lastAnchor`（上一次单击的图片 id）
- Shift+点击 C：选中从 anchor 到 C 在**当前显示顺序**中的所有图片
- 若无 anchor，则退化为单选
- 幂等：再次 Shift+点击同一目标不产生重复

### 6. 框选（橡皮筋选择）

**实现方式**：
- 在图片容器上监听 `mousedown`（左键且非 Ctrl/Shift）→ 记录起点 → 进入框选态
- `mousemove` → 绘制绝对定位的半透明选择框（`position: fixed`，跟随视口坐标）
- 命中检测：遍历当前图片卡片的 `getBoundingClientRect()`，与选择框求交集
- `mouseup` → 结束，应用选择（默认替换；按住 Ctrl 则叠加）
- 阈值：拖动距离 < 4px 视为普通点击，不触发框选
- 滚动容器内：框选期间禁用文本选择（`user-select: none`）

**难点**：瀑布流用 `transform` 显式定位，`getBoundingClientRect()` 依然有效（返回实际视口坐标），
所以命中检测无需特殊处理——这是选择用 rect 而非布局数据的原因。

### 7. 拖出到资源管理器（复制）⭐ 关键风险点

**问题**：浏览器/WebView 中，HTML5 `dataTransfer` 出于安全限制**无法设置真实文件路径**，
`DataTransferItem` 只能携带二进制内容（`getAsFileSystemHandle` 也仅 Chromium 且需用户授权）。

**可行方案（按推荐度）**：

| 方案 | 可行性 | 代价 |
|------|--------|------|
| **A. 壳层原生拖出**（推荐） | ✅ 可行 | 需用 Windows `DoDragDrop` + `IDataObject`(CF_HDROP)，壳层已引入 `windows` crate，与刚做的拖入模块同源 |
| B. `webview.start_drag()` | ⚠️ Tauri 2 有 `drag` 权限但 API 面窄，主要面向文件拖出且功能受限 | 需试 |
| C. 复制到临时目录 + 提示 | ⚠️ 曲线方案，体验差 | 低 |

**方案 A 细节**（与现有 `drag_drop.rs` 对称）：
1. 前端 `mousedown` 在已选图片上 + 移动超过阈值 → `invoke('start_file_drag', { ids })`
2. 壳层用 `SHCreateDataObject` 或自建 `IDataObject`（`CF_HDROP`，指向 `data/library` 下的真实文件）
3. 调用 `DoDragDrop(hwnd, dataObj, DROPEFFECT_COPY, ...)`，`DROPEFFECT_COPY` 即默认复制
4. 释放后返回结果；**无确认步骤**（符合需求）

> ⚠️ 注意：`DoDragDrop` 会阻塞调用线程直到拖放结束，必须跑在**非 UI 线程**或按 COM 要求处理消息循环。

## 三、需要你确认的决策点

1. **拖出方案**：是否接受用**壳层原生实现**（方案 A，最可靠）？还是先做前端版试试（可能不成功）？
2. **单击缩略图**：保持"打开详情"不变？还是也改为选择（信息区才选择）？
3. **框选起点**：只在**空白区域**按下才框选，还是在图片上按下也能框选（更接近资源管理器，但与"拖动图片"冲突）？
4. **拖动与框选冲突**：在已选图片上拖动 = 拖出文件；在图片上拖动 = ？建议：**已选图片→拖出；未选中图片→从该图开始框选**。
5. **主目录页**：是否同样改造（它当前是"卡片 + 复选框"结构，与图库不同）？
