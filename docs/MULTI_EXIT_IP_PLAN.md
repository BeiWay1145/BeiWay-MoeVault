# 增强2：Clash 用户多出口 IP 轮换方案（规避 SauceNAO 单 IP 限流）

> 状态：**方案待确认**（本文档只做可行性论证与交互设计，尚未实施）。
> 请先阅读第 6 节「需要你确认的点」，确认后再进入实现。

## 1. 背景与问题

SauceNAO 免费账号的限流是**按出口 IP** 计算的：

```
免费账号：4 次 / 30 秒（全局 IP 池），100 次 / 日
```

本项目现有的 `keypool.rs` 已实现：
- **多 API key 轮换**（每 key 独立冷却与日配额）
- **全局窗口**：跨 key 共享 4 次/30 秒的限制（`DEFAULT_GLOBAL_LIMIT = 4`）

**但多 key 无法突破 IP 限制**：SauceNAO 的 4 次/30 秒 是按来源 IP 算的，
再多 key 也是同一个 IP 在请求。真正的瓶颈是**出口 IP 只有一个**。

## 2. 可行性结论

**可行。** 依据：

| 条件 | 现状 | 结论 |
|------|------|------|
| 本机有 Clash 类代理 | 用户已确认使用 Clash | ✅ |
| Clash 支持多出口 | Clash/Mihomo 支持 `mixed-port` + 多节点/多 `proxy-provider` | ✅ |
| 可指定出口 | 通过 **Clash 的本地 HTTP 代理端口** 或 **策略组切换** 实现 | ✅ |
| 程序可指定代理 | 现有 HTTP 客户端（reqwest）支持 `Proxy::all()` | ✅ 无需改网络层 |

**关键约束**：reqwest **不能**在单次请求中指定"用哪个代理"，
但可以**按请求构造不同的 Client**（每个 Client 绑定一个代理 URL）。
因此实现方式是：**为每个出口 IP 维护一个 Client**，调度时选一个。

## 3. 两种实现路径（推荐 A）

### 路径 A：多个本地代理端口（推荐）

用户预先在 Clash 里配置多个 **固定出口** 的入站端口，例如：

```yaml
# Clash 配置片段（用户自行维护）
proxies:
  - name: "JP-1"
    type: ss
    server: jp1.example.com
    # ...
  - name: "US-1"
    type: ss
    server: us1.example.com
    # ...

proxy-groups:
  - name: "SauceNAO-1"
    type: select
    proxies: ["JP-1"]
  - name: "SauceNAO-2"
    type: select
    proxies: ["US-1"]

# 关键：为每个出口开一个独立入站端口
listeners:
  - name: sauce-1
    type: mixed
    port: 7901
    proxy: "SauceNAO-1"     # 固定走 JP-1
  - name: sauce-2
    type: mixed
    port: 7902
    proxy: "SauceNAO-2"     # 固定走 US-1
  - name: sauce-3
    type: mixed
    port: 7903
    proxy: "SauceNAO-3"
```

**应用侧**：用户只填 3 个端口号（7901/7902/7903），应用建 3 个 Client，
每次请求轮换一个 → **每个出口独立计算 4 次/30 秒** → 理论吞吐 ×3。

**优点**：
- 出口**完全可控**（用户明确知道走哪几个节点）
- 与 Clash 的"自动选择"解耦，不会中途换 IP
- 不受 Clash 版本差异影响（`listeners` 是标准能力）

**缺点**：需要用户手动加几行配置（但我们可以给出一键复制的模板）。

### 路径 B：Clash 外部控制 API 切换策略组

通过 Clash 的 RESTful API（默认 `127.0.0.1:9090`）切换策略组的选中节点：

```
PUT /proxies/{groupName}   body: {"name": "JP-1"}
```

**应用侧**：每次请求前调 API 切换，再用同一个端口发请求。

**优点**：用户零配置（只需填 API 地址 + secret）。

**缺点（较严重）**：
- **切换是有延迟的**：Clash 需要重建连接，且切换后**全局生效**——
  会影响用户其它正在使用代理的程序（浏览器等），属于**干扰用户**的行为
- 高频切换可能触发 Clash 的连接风暴
- 不同 Clash 分支（Clash Verge / Mihomo / Clash for Windows）API 行为有差异

**结论：不推荐 B，除非用户明确表示可接受全局切换干扰。**

## 4. 交互设计（路径 A）

```
│  启用多出口轮换        [ 开关 ]                       │
│                                                      │

│  ┌────────────────────────────────────────────┐      │
│  │ 7901                                       │      │
│  │ 7902                                       │      │
│  │ 7903                                       │      │
│  └────────────────────────────────────────────┘      │
│  [ 添加端口 ]  [ 测试全部 ]                           │
│                                                      │
│  端口 状态       出口 IP          最近延迟             │
│  ─────────────────────────────────────────────────   │
│   7901  ✅ 正常   203.0.113.7     128 ms             │
│   7902  ✅ 正常   198.51.100.23   245 ms             │
│   7903  ⚠️ 失败   —               —                  │
│                                                      │
│  [ 显示 Clash 配置模板 ]                              │
└──────────────────────────────────────────────────────┘
```

### 4.2 交互要点

1. **只允许填端口号，不填完整 URL**
   应用固定拼成 `http://127.0.0.1:{port}`。这样：
   - 避免用户填入任意外部代理（安全考虑）
   - 交互最简单（用户只需从 Clash 配置里抄端口数字）

2. **限制数量（建议 2–8 个）**
   - 少于 2 个：轮换无意义（等于单出口）
   - 多于 8 个：SauceNAO 免费额度是 100 次/日（按账号），
     IP 再多也受账号日配额限制，收益递减且管理复杂

3. **必须能"测试全部"**
   逐个端口发一个轻量请求（如 `https://api.ipify.org`），显示：
   - 该端口的**出口 IP**（让用户确认各端口确实走不同节点）
   - 延迟与可用性
   - **若多个端口出口 IP 相同 → 明确警告**（说明 Clash 配置没生效，轮换无意义）

4. **提供一键复制的 Clash 配置模板**
   点击后在弹窗里展示可直接粘贴的 `listeners` 片段（端口按用户填写的生成）。

### 4.3 调度侧行为（对用户透明）

- 启用后：`keypool` 的每次请求轮换一个出口（round-robin）
- **全局窗口计算方式改变**：
  ```
  旧：4 次 / 30 秒（所有 key 共享，因为同一 IP）
  新：4 次 / 30 秒 **每个出口**（N 个出口 → 理论 4N 次 / 30 秒）
  ```
- 单出口失败（超时/连不上）→ 该出口临时标记不可用，**自动跳过**，
  连续失败若干次后告警（不静默吞掉）

## 7. 风险与限制（需要你知晓）

1. **SauceNAO 账号日配额才是硬上限**
   免费账号 100 次/日是**按账号**算的，多出口不能突破。
   多出口只解决"**4 次/30 秒**"的瞬时限制 → 让**打标更快**，不增加总量。

2. **可能触发风控**
   同一账号从多个国家 IP 高频请求，SauceNAO 有可能判定异常。
   建议：出口节点尽量选**相近地区**，并保持温和的请求节奏。

3. **代理稳定性**
   免费/低质节点会超时，导致溯源失败率上升。
   因此"测试全部"功能是必需的，且失败出口要能自动跳过。

4. **不改变缓存策略**
   已溯源的图有 `sauce_cache`，不会重复请求——这是节省配额的主力，
   轮换只是补充手段。
